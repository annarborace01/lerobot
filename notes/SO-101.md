# Some high level summaries

## Goals:
- Develop a robust neural network–based policy that can control a robot arm to pick up a Lego brick and place it into a bowl.

- Maintain that level of robustness while using as little training data as possible.

- Improve interpretability of the model’s behavior by adding additional outputs such as Chain-of-Thought reasoning, 3D reconstruction, etc.

## Thoughts:
- Honestly, I think the model I trained is just an average performer that has overfitted to the training data. It doesn’t generalize well and can’t handle unseen scenarios. I feel that this whole imitation-learning approach is very similar to NeRF or Gaussian-splitting training. It tightly overfits to the training scene and shows limited generalization when imagining unseen scenarios, but it doesn’t truly understand the task. Once the evaluation scenario falls outside the training distribution, the method breaks down. For example, it may be trained to place LEGO bricks into a red bowl, but when two bowls appear in the scene, its behavior becomes completely unreasonable. A human, by contrast, would make a much more sensible decision.

- Choosing the training dataset is particularly interesting. Pretraining an LVM model can leverage all kinds of data, but for task-specific fine-tuning, the effects are less predictable. You might see clear behavioral improvements with certain data—such as varying bowl positions—but with other data, the outcome is uncertain, especially when the collected demonstrations lack consistent trajectories across different people. Will more such data get more robust behaviors?  

- The model struggles to learn from just a few episodes and generalize to a simple task. Humans can easily do this, so we must not be leveraging data and compute effectively. Needing so much data and computation to learn such a simple task feels inefficient. Maybe I should try a large pre-trained model like Pi, but I don’t have an edge device capable of running the model for inference.

- When trained only on the task of placing a single red Lego brick into a red bowl, the model can still place a yellow Lego brick into a blue bowl. There are no language instructions involved, so it seems the model learns shape information rather than just color.

- My first model was trained on just two episodes, and surprisingly, it couldn't open its gripper at the end. This makes me wonder if we should apply the same loss function as in imitation learning to predict a sequence of actions. It seems some actions are more crucial than others, which might align with reinforcement learning’s value function for encouraging good behaviors.

- Action chunking leads to discontinuities. This makes sense, as the model predicts actions in 1-second chunks, and the new actions may not align with previous ones. This resembles a motion planning problem where we have infrequent global position updates and more frequent local updates. The goal is to maintain smooth motion by updating both.

- The original Lerbot tutorial suggests "maintaining consistent grasping behavior throughout the recordings," but I disagree. High-quality, diverse data is more important. I had multiple people, including kids, help collect many episodes. This ties back to the imitation learning loss—different trajectories can still achieve the same goal. We might need rewards to guide the model, or at the very least, penalize deviations.

- The tutorial also recommends that "a good rule of thumb is you should be able to do the task yourself by only looking at the camera images." I don’t agree with this either. For example, it’s definitely easier to grasp an object using 3D models than by only looking at 2D camera images. With two cameras, the model should ideally learn to use 3D perception. Decoding a 3D scene might be a useful way to validate if the model's output makes sense.

- Error handling is an issue—the model struggles with unexpected errors outside the training distribution. To improve this, we may need to incorporate reinforcement learning techniques. But I need to think about how to ensure safety when applying RL with real hardware—I don’t want the robot arm making random, unsafe actions. It seems like having a model that can decide when to stop or continue trying would be helpful.

- I should try Qwen models to see if they perform better. And I hope to add Chain-of-Thought (CoT) reasoning to better decode its behavior.

## Engineering issues
- Disassembling the SO-101 arm for debugging is extremely difficult, so ensure the motors are functioning correctly before assembling the arm.
- I struggled with USB bandwidth limitations for a while while trying to stream images from two cameras through a single USB hub.
- The camera devices' names and IDs are identical, which causes issues with my udev rules.
- I need to add an emergency stop button.
- I can't deploy a large model on an edge device.

It is quite annoying to check which ttyACM file is which arm. Now let's start to use udev rules to make it easy to access different devices

```
udevadm info -a -p $(udevadm info -q path -n /dev/ttyACM0)
```

- Write udev rules
```
sudo nano /etc/udev/rules.d/99-usb-serial.rules
```

- Note that oftentimes the video has a main stream and a meta stream. We assume the main stream is index 0 below.
```
# Device 1
SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="55d3", ATTRS{serial}=="5A7C118778", SYMLINK+="leader_arm"

# Top Camera
SUBSYSTEM=="video4linux", KERNEL=="video*", KERNELS=="3-2.3", ATTRS{idVendor}=="0c45", ATTRS{idProduct}=="64ab",  ATTR{index}=="0", SYMLINK+="top_camera"
# Front Camera
```

# On Mac M chips

if you’re on macOS ARM, if you’re on macOS ARM:
```
conda install pytorch torchvision -c pytorch
```
```
python -c "import platform; print(platform.platform())"
```
If it shows:
`macOS-14.x-arm64-...`
✅ you’re running native Apple Silicon (good).

If it shows:
`macOS-14.x-x86_64-...`
⚠️ you’re running under Rosetta. You’ll need to create a new arm64 conda environment.
It is just that `pip install lerobot==0.4.0` might fail due to using an old torch version 

```
CONDA_SUBDIR=osx-arm64 conda create -n lerobot-arm python=3.10
conda activate lerobot-arm
conda install pytorch torchvision torchaudio -c pytorch -c conda-forge
```

Binaries are installed at
```
ls /Users/xipengwang/miniconda/envs/lerobot-arm/bin/lerobot-find-port
```

⚠️: You might need to change `Privacy & Security to allow accessories to Connect` to make sure you can find the control
board USB devices. 
```
ls  /dev/tty.usbmodem*
```

Might need to change:
```
sudo chmod 777 /dev/tty.usbmodem5A7C1166181 follower 
sudo chmod 777 /dev/tty.usbmodem5A7C1187781 leader
```

```
lerobot-setup-motors \
    --robot.type=so101_follower \
    --robot.port=/dev/tty.usbmodem5A7C1166181
```

```
lerobot-calibrate \
    --robot.type=so101_follower \
    --robot.port=/dev/tty.usbmodem5A7C1166181 --robot.id=xipeng_follower_arm
```

```
lerobot-setup-motors \
```

```
    --teleop.port=/dev/tty.usbmodem5A7C1187781 --teleop.id=xipeng_leader_arm
```
